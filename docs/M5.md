La version évaluée doit être la version actuelle ; son `snapshot` est la source du titre, équipe, challenge, problème, solution, technologies et pitch. Livrables : `Submission.deliverables`, fichiers dans le stockage privé M3.

## Fonctionnalités

Grille personnalisable avec critères décimaux, validation de la somme des poids (100), ajout/retrait de critères, seuil d’écart et minimum de jurés. La grille et les paramètres sont figés dès le premier brouillon. Configurez-les avant de commencer la campagne.

Affectations idempotentes à des jurés actifs de l’édition, uniquement sur les versions officielles actuelles ; retrait avant validation, réaffectation par retrait puis nouvelle affectation. Un membre de l’équipe ne peut pas la noter. Déclaration et résolution humaine des autres conflits, historique nominatif. Une affectation validée est conservée.

Espace jury : compteurs, hackathons, projets, brouillons, notes validées ; contenu figé M3 et téléchargement privé contrôlé pour chaque fichier. Un juré accède uniquement à ses affectations. Commentaires et notes individuels réservés au juré et aux organisateurs autorisés.

Notation : brouillon partiel ou validation complète et définitive. Calcul serveur en Decimal : somme `(note / maximum) * poids`, total individuel conservé à quatre décimales ; moyenne arithmétique des totaux validés, arrondi `ROUND_HALF_UP` à deux décimales. Le calcul navigateur est uniquement une estimation.

Classement provisoire privé : tous les projets officiellement soumis, score, nombre de jurés, complétude. Égalités au centième : rang partagé de compétition (1, 1, 3) ; identifiant projet utilisé uniquement pour stabiliser l’affichage.

Divergences : écart max–min entre totaux validés sur 100 ; alerte à partir du seuil inclus. Résolution motivée par un organisateur ; elle expire si les affectations/évaluations changent. `services.copilot_input` prépare un contrat consultatif pour intelligence, sans API IA nécessaire et sans écriture automatique.

Validation du classement puis publication explicite : poids validés, délai de soumission dépassé, minimum de jurés et toutes les notes validées, aucun conflit bloquant ou rôle révoqué, divergences vérifiées. Les affectations obsolètes après réouverture M3 bloquent aussi la publication. Un classement modifié doit être revalidé. Historique versionné figé et page publique ne contenant que les agrégats.

Prix : nom, description, partenariat M1 confirmé facultatif. Un seul gagnant par prix, plusieurs prix distincts possibles pour un projet. Attribution définitive depuis la dernière version publiée. Attribution identique répétée idempotente. Les gagnants sont attachés à leur version de publication ; les versions précédentes restent consultables.

Les écritures métier s’exécutent dans des transactions verrouillant l’utilisateur puis le hackathon, dans l’ordre utilisé par M2/M3. Les actions sensibles sont POST avec CSRF. L’administration M5 est en lecture seule ; les opérations passent par les pages métier.

## Installation et vérification

Dans la racine du dépôt (environnement uv existant) :

```powershell
uv run --no-sync manage.py check
uv run --no-sync manage.py makemigrations --check --dry-run
uv run --no-sync manage.py migrate --plan
uv run --no-sync manage.py migrate evaluations
uv run --no-sync manage.py test evaluations --settings=evaluations.test_settings --noinput
uv run --no-sync manage.py test evaluations projects accounts hackathons teams mentoring core --settings=evaluations.test_settings --noinput
uv run --no-sync manage.py runserver
```

Si le cache uv est inaccessible, utiliser `.venv/Scripts/python.exe` à la place de `uv run --no-sync`.

`evaluations.test_settings` crée une base PostgreSQL de test au nom aléatoire à chaque exécution. Cela évite de réutiliser ou supprimer `test_hackflow_db`, susceptible d’être utilisée par un collègue. PostgreSQL doit être disponible et l’utilisateur de développement doit pouvoir créer une base de test. Les tests créent leurs fixtures exclusivement dans cette base éphémère et Django la retire à la fin.

## Parcours navigateur avec les données réelles

1. Lancer le serveur puis se connecter comme organisateur d’un hackathon existant. Ouvrir sa gestion M1 et donner le rôle **Jury** aux utilisateurs concernés dans **Rôles**. Ne pas leur donner le rôle participant dans la même édition.
2. Les participants créent leurs équipes et projets via M2/M3, ajoutent les livrables et officialisent leur version. Aucun jeu de données M5 n’est injecté.
3. Ouvrir **Jury & résultats** dans la navigation ou **Jury, évaluations et prix** dans le pilotage M1.
4. Choisir le hackathon, ouvrir **Grille**, définir tous les critères (poids total 100), maximums, seuil et minimum de jurés ; cliquer **Valider la grille**.
5. Dans **Affectations**, sélectionner une soumission officielle et un juré, puis répéter pour chaque projet/juré. Vérifier les projets sans juré.
6. Se connecter comme juré ; ouvrir **Mon espace jury**, puis **Consulter et noter**. Vérifier le contenu officiel et télécharger les livrables. Saisir des notes, enregistrer un brouillon, puis **Valider définitivement**.
7. Au besoin, le juré déclare un conflit depuis sa carte ; l’organisateur le résout avec justification ou retire l’affectation avant validation.
8. L’organisateur suit la progression dans **Pilotage**, consulte les évaluations depuis **Affectations** et traite les alertes dans **Vérifications**.
9. Après la date limite M1 et la fin des évaluations, ouvrir **Classement**, cliquer **Valider ce classement**, puis **Publier officiellement la version N**. Toute incohérence apparaît comme une erreur explicite.
10. Dans **Prix**, créer les récompenses, éventuellement liées aux partenariats M1 confirmés, et sélectionner les gagnants. L’attribution est définitive.
11. Les participants ouvrent la fiche publique M1 du hackathon puis **Résultats officiels**. Seuls le classement publié et les lauréats sont affichés ; les anciennes versions sont accessibles.

## Limites explicites

Pas de fournisseur IA activé : la détection déterministe fonctionne seule. Pas de réouverture d’une note validée ni de modification d’un prix attribué : ces décisions sont définitives. Une nouvelle version officielle M3 nécessite une nouvelle affectation et une nouvelle évaluation ; les anciennes notes restent conservées. Les traductions anglaises des nouveaux écrans M5 ne sont pas encore livrées.
